# 콘텐츠 심사 QA 주간 리포트 자동화

> 심사원 QA 데이터에서 **KPI 계산 → 불일치 원인 분류(로컬 LLM) → 주간 One-pager 작성**까지 자동으로 만드는 파이프라인입니다.
> 실제 업무 구조를 참고했지만, **데이터는 전부 가상으로 새로 만들었습니다.** (실제 고객사 데이터·정책명·사유 문장 미사용)

실행 결과 수치는 [RESULTS.md](RESULTS.md)에 자동으로 정리됩니다.

---

## 1. 문제 (As-Is)

콘텐츠 심사 QA 업무에서 매주 반복하던 리포트 작업입니다.

1. 심사 로우데이터 내려받기 (케이스 ID, 심사원 태그, Arbi 태그, 어필 사유, 어필 결과)
2. 심사원 태그와 Arbi 태그가 다른 건 추리기
3. 어필 사유를 한 건씩 읽고 원인 분류
4. 정확도 계산, 원인 정리, One-pager 작성

- 소요 시간: **1주치 리포트 115분** (가상 데이터로 수작업 1회 실측)
- 문제점: 원인 분류가 사람마다 다르고, 정책 변경 같은 신호를 늦게 발견함

## 2. 해결 (To-Be)

```
raw_cases.csv
   │
   ├─ step1  KPI·혼동 패턴·취약 심사원 계산 ............ 코드 (LLM 없음)
   ├─ step2  어필 사유 → 원인 5종 분류 ................. 로컬 LLM (Ollama)
   ├─ step3  정답지로 채점, 7B vs 3B 비교 .............. 코드
   └─ step4  주간 One-pager(HTML) 생성 ................ 코드 + LLM 요약 + 숫자 검증
```

- 소요 시간: **1주치 리포트 약 1분** (평균, 가장 많은 주도 약 2분) → **약 99% 단축**, 사람은 결과 검토만
  - 주차별 실측: LLM 원인 분류 23~99초 (어필 10~44건, 평균 52초) + One-pager 생성 7~10초
  - 모델을 처음 메모리에 올리는 시간은 제외 (측정하지 않음)
  - 7B·3B 비교까지 포함한 `run_all.ps1` 8주치 전체: 약 14분 (RTX 4070 Super)

## 3. 설계에서 신경 쓴 점

**① 정답을 아는 가상 데이터로 검증**
`make_sample_data.py`가 패턴을 일부러 심어서 데이터를 만듭니다. 취약 심사원 2명, 4주차 SOP 개정, 5주차 정책 변경, 자주 헷갈리는 태그 쌍입니다. 파이프라인이 이 패턴을 실제로 찾아내는지 확인할 수 있고, 어필 원인 정답지(`answer_key.csv`)로 LLM 분류 정확도를 숫자로 잽니다. 정답지와 어필 결과는 모델에 보여주지 않습니다.

**② 숫자는 코드가, 문장은 LLM이**
KPI, 순위, 비율은 전부 코드가 계산합니다. LLM은 계산된 사실 목록만 받아 요약 문장을 씁니다.

**③ LLM 환각 검사**
LLM이 쓴 문장 속 숫자를 사실 목록과 하나씩 대조합니다. 목록에 없는 숫자가 있으면 그 문장을 버리고 규칙 기반 문장으로 대체합니다. 리포트 상단에 "검증 통과 / 대체됨"이 표시됩니다.

**④ 모델 크기 비교 후 선택**
같은 PC(RTX 4070 Super)에서 qwen2.5 7B와 3B를 같은 정답지로 채점했습니다. 결과는 [RESULTS.md](RESULTS.md) 2장에 있습니다.

**⑤ 1단계로 안 보이는 신호를 2단계가 잡음**
5주차 정책 변경은 정확도 숫자에는 거의 드러나지 않고, 어필 원인 비율에서만 보입니다. LLM 원인 분류가 필요한 이유입니다.

## 4. 실행 방법

준비물: Python 3.10+, [Ollama](https://ollama.com), 모델 `qwen2.5:7b`, `qwen2.5:3b`. 추가 패키지 설치는 없습니다.

```powershell
ollama pull qwen2.5:7b
ollama pull qwen2.5:3b
powershell -ExecutionPolicy Bypass -File .\run_all.ps1
```

단계별로 따로 실행할 수도 있습니다.

| 파일 | 하는 일 | 결과 |
|---|---|---|
| `make_sample_data.py` | 가상 데이터 + 정답지 생성 | `raw_cases.csv`, `weekly_kpi.csv`, `answer_key.csv` |
| `step1_kpi_analysis.py` | KPI, 혼동 패턴, 취약 심사원 | `output/kpi_by_week.csv` 외 |
| `step2_root_cause_llm.py --model <모델>` | 어필 사유 원인 분류 | `output/root_cause_<모델>.csv` |
| `step3_compare_models.py` | 정답지 채점, 모델 비교 | `output/model_comparison.csv` |
| `step4_onepager.py --week <N>` | 주간 One-pager | `output/onepager_week<N>.html` |
| `make_results_md.py` | 결과 요약 문서 | `RESULTS.md` |

## 5. 한계와 다음 단계

- 가상 데이터라 실제 사유 문장보다 표현이 단순합니다. 실제 적용 시에는 정답지를 사람이 일부 라벨링해서 다시 채점해야 합니다.
- 7B가 자주 틀린 유형: "정책을 몰랐다"를 "SOP가 모호했다"로 분류. 원인별 예시를 프롬프트에 넣는(few-shot) 개선 실험이 다음 단계입니다.
- 정답지 일부 문장도 사람이 읽기에 애매한 경우가 있어, 라벨 품질 점검이 필요합니다.
- **숫자 검증의 한계:** 근거 없는 숫자는 잡지만, 맞는 숫자를 잘못 설명하는 오류는 못 잡습니다. 실제로 5주차 요약에서 "직전 3주 평균 0.7건"을 "전주 평균"으로, 바뀐 보정 정확도를 "유지"로 쓴 사례가 있었습니다. 숫자마다 이름표(예: `3주평균=0.7`)를 붙여 대조하는 방식으로 보완할 수 있고, 그 전까지는 사람이 최종 검토해야 합니다.
